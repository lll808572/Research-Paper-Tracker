# CLEW: Log-Anchored Backward Tracing for Root-Cause Code Localization

## 1. 基本信息

作者、年份与标识见元数据。首次提交：2026-11-14 15:10:10 UTC（北京时间 23:10:10）。正式发表及录用未核实；按预印本收录。arXiv DOI 标 pending registration，doi 留空。[元数据](https://arxiv.org/abs/2611.19448)

## 2. 一句话总结

先把日志锚定到代码，再由 Agent 向上游追溯候选故障函数，并保留证据链接。[摘要与 §II](https://arxiv.org/html/2611.19448v1)

### 2.1 摘要中文翻译

翻译范围：摘要要点译述，非逐句全文翻译；依据 [arXiv v1 摘要](https://arxiv.org/abs/2611.19448)，不混入个人评价。

生产故障难以复现，日志也可能嘈杂或缺失。CLEW 先以规则连接日志与源码，再由 LLM 引导逆向追溯，输出候选函数和证据解释。作者在 LogLoc 的真实 issue 与故障注入案例上评估，报告了具有竞争力的定位表现和运行效率；结论限于所测试条件。

### 2.2 数据集—问题—解决方案

| 数据集或实际数据 | 数据类型与任务 | 要解决的具体问题 | 解决方案及作用机制 | 验证依据与边界 |
|---|---|---|---|---|
| LogLoc-Issues：150 个真实 issue | issue 内嵌日志及源码；函数级缺陷定位 | 症状代码不一定是故障代码，线索可能不完整 | 规则日志锚定、诊断状态、Agent 上游源码探索及候选排序 | §III-B、§IV；修复函数仅是根因代理标签，Acc@1 的领先未达统计显著 |
| LogLoc-Airflow：42 个注入案例 | 多进程日志、症状描述及源码；已知注入函数定位 | 从日志症状追溯到上游缺陷位置 | 同一框架对完整日志进行证据选择和锚定，再引导追溯 | §III-B/E；消融同时改变证据选择与锚定，不能把差异单独归功于锚定 |

串联理解：针对 LogLoc 两类案例中的“症状位置与缺陷位置不一致”，作者提出日志锚定加 Agent 追溯；实验评估定位和效率，但没有证明返回的机制路径就是实际因果链。[正文 §II–V、VII](https://arxiv.org/html/2611.19448v1)

## 3. 研究背景

记录报错的函数可能只是传播链下游。[§I](https://arxiv.org/html/2611.19448v1#S1)

## 4. 研究问题

缺少可复现故障和测试覆盖信息时，如何利用 issue、日志及源码定位缺陷？[§I/II-B](https://arxiv.org/html/2611.19448v1)

## 5. 核心方法

### 5.1 整体框架

规则锚定 → Agent 逆向源码探索 → 排序和解释。[§II](https://arxiv.org/html/2611.19448v1#S2)

### 5.2 关键模块

源码观测点索引、代码图、日志诊断状态和机制路径；锚定分数不是校准概率。[§II-C](https://arxiv.org/html/2611.19448v1#S2)

### 5.3 数学公式

原文 §II-B 将输出表示为：

$$C=[(c_1,s_1),\ldots,(c_k,s_k)].$$

其中 $c_i$ 为函数、$s_i$ 为定位分数；另输出模块及解释。

### 5.4 数据输入与输出

输入 issue、日志、部署源码快照；输出候选函数和关联日志证据。[§II-B](https://arxiv.org/html/2611.19448v1#S2)

### 5.5 技术路线

从症状位置沿代码关系追溯，而非直接把报错位置当根因。

## 6. 创新点

作者主张：结构化日志引导调查并保留可检查证据。助手评价：解释是否可追溯、是否因果正确、定位是否准确，应分别评价。

## 7. 实验设计

LogLoc：150 个真实 issue、42 个 Airflow 注入案例。对照 Base、LocAgent、Agentless；指标 Acc@K、Recall@5、MRR；消融移除结构锚定或 Agent。[§III](https://arxiv.org/html/2611.19448v1#S3)

## 8. 关键实验结果

LogLoc-Issues：Acc@1 为 77.3%，LocAgent 为 72.0%，差异未达统计显著；Recall@5 反而较低。去除结构锚定的准确率差异亦不显著。[§I、§IV-B](https://arxiv.org/html/2611.19448v1)

## 9. 局限性

### 作者明确承认的局限性

修复位置只是根因代理标签；结构证据检查不证明解释的因果正确性。[§VII](https://arxiv.org/html/2611.19448v1#S7)

### 自己的分析

它研究函数级缺陷定位，不能直接等同于多变量时序的因果根因识别。若迁移到工业指标诊断，必须重新定义节点、证据与真值。

## 11. 对研究的启发

以下为助手建议，尚未验证：

- 可借鉴方法：为 Agent 的每个诊断候选保存原始证据位置。
- 可迁移模块：证据到节点的锚定、路径输出及结构检查。
- 值得开展的实验：时序异常窗口 → 关联日志/服务节点 → Agent 排查；对照只有数值、只有日志、二者融合，固定模型和调用预算。
- 潜在研究问题：正确根因是否真的由已查看证据支持？同时衡量根因命中、证据覆盖与无依据结论比例，避免只优化答案准确率。
